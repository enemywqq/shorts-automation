# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Оркестратор-конвейер: исходное видео → вертикальные клипы → очередь в SQLite → заливка в TikTok с отложенной публикацией. Свой код только в `app/`. Два внешних инструмента лежат в `tools/` как git submodules. Их вызываем исключительно через `subprocess`, у каждого свой `.venv`. Код сабмодулей не правим. Единственное исключение: патч генератора `patches/shorts-generator.patch`.

Пожелания владельца: минимально рабочее решение, без лишних абстракций, все настройки в одном файле ([app/config.py](app/config.py)), только stdlib. Общение, комментарии в коде и сообщения CLI — на русском. Уведомления в Telegram запланированы на самый конец, пока их не трогать.

## Навыки (обязательно)
- Любой код: используй навык ponytail.
- Ответы мне в чате: используй навык caveman.
- Любой текст, который остаётся в проекте (README, документация, комментарии, сообщения коммитов, подписи к видео): прогоняй через навык humanizer.
- Никогда не используй точку-разделитель между словами ("·") ни в каком тексте.

## Правила кода
- Без оверинжиниринга. Минимальное решение, которое работает в реальном сценарии. Никаких абстракций, классов и слоёв «на будущее».
- Не трогай tools/ (сабмодули). Если без правки внутри них не обойтись, сначала спроси. Согласованные правки генератора живут только в `patches/shorts-generator.patch`: поправил файл сабмодуля, значит, пересобери патч (`git -C tools\shorts-generator diff --output=..\..\patches\shorts-generator.patch`).
- После обновления сабмодуля генератора проверь, что патч применяется к чистому сабмодулю: `git -C tools\shorts-generator apply --check ..\..\patches\shorts-generator.patch`. Если не применяется, сначала спроси, как переносить правки.
- Чужие инструменты вызываем только через subprocess с python из их собственного .venv. Не импортируем их код в наш.
- Пути только через pathlib, без хардкода абсолютных путей. Всё настраиваемое лежит в одном конфиге, секреты в .env, в код их не пишем.
- Не добавляй новые зависимости без моего согласия.
- Type hints в сигнатурах функций. Функции короткие, одна задача на функцию.
- Ошибки не глотаем: никаких голых except. Ошибку внешнего инструмента логируем вместе с его stderr и записываем в БД.
- Заливку со статусом unknown («возможно, опубликовано») никогда не повторяем автоматически.
- Логи (ход работы, ошибки, предупреждения) через logging. Вывод, который команда показывает пользователю как результат (таблица status, итоговые сообщения), через print.
- Комментарии только там, где неочевидно «почему». «Что делает код» не комментируем.

## Коммиты
Формат Conventional Commits: `тип(область): описание`

Типы:
- feat: новая функциональность
- fix: исправление ошибки
- refactor: изменение кода без изменения поведения
- docs: документация
- chore: настройки, зависимости, сабмодули, мелкие служебные правки
- test: тесты

Область указывает, какую часть проекта затрагивает коммит: queue, upload, process, config, db, cli, readme, tools. Если коммит затрагивает весь проект, область не пишем.

Описание:
- на русском, с маленькой буквы, без точки в конце, до 72 символов;
- пишем, что сделано, а не что нужно сделать: «добавлена», «реализован», «исправлена», «удалён». Нельзя: «добавить», «сделать», «TODO»;
- без длинных тире, без эмодзи, без канцелярита и пустых слов вроде «улучшен код» или «небольшие правки».

Если одной строки мало, после пустой строки идёт тело: коротко, почему сделано именно так. Что именно изменилось, видно в диффе, это не пересказываем.

Примеры:
feat(upload): реализована заливка с отложенной публикацией через -sc
fix(process): исправлена перезапись клипов при повторном запуске
refactor(db): статусы клипов вынесены в константы
docs(readme): добавлена инструкция по тестовому прогону
chore(tools): обновлён сабмодуль tiktok-uploader

fix(upload): клип помечается unknown до вызова аплоадера

Если процесс прервётся посреди заливки, клип не уйдёт повторно
автоматически и не создаст дубль.

## Команды

Windows, PowerShell, из корня проекта. Своего venv у оркестратора нет. Два модуля с зависимостями, `app/faces.py` (OpenCV) и `app/gemini.py` (google-genai), запускаются python из venv генератора и в оркестратор не импортируются.

```powershell
py -3.13 -m app process <путь|URL> [--layout auto|fit|crop] [--type stream|film] [--streamer <ник>]
                                     # генератор → заголовки Gemini → монтаж ffmpeg → строки в БД
py -3.13 -m app cut [<путь|URL>] [--layout ...] [--type ...] [--streamer ...] [--ask]
                                     # то же в data/preview, без БД; открывает папку
py -3.13 -m app upload               # все pending → свободные слоты → autotok с -sc
py -3.13 -m app status
py -3.13 -m app retry <id> [<id>...] # только failed/unknown → pending
```

Тестов и линтера нет. Логику без реального TikTok проверяют так: в скрипте-обёртке подменяют `config.DB_PATH`, `config.CLIPS_DIR`, `config.GENERATOR_DIR`/`GENERATOR_PYTHON` и `config.UPLOADER_DIR`/`UPLOADER_PYTHON` на временную папку с фейковыми `main.py` и `cli.py`, а `render` подменяют на копирование файла.

Установка инструментов описана в [README.md](README.md). Инструменты вызываются как `tools\<tool>\.venv\Scripts\python <entry>` без активации venv.

## Архитектура и неочевидные связи

**Генератор** (`tools/shorts-generator`, `main.py --mode local`):
- Режим по умолчанию у него `api` (платный MuAPI), поэтому `--mode local` передаётся всегда.
- Запускается с `cwd=GENERATOR_DIR`. Папку вывода задаёт env `LOCAL_OUTPUT_DIR` — она перекрывает его `.env`, потому что `load_dotenv` вызывается без override.
- Папка вывода `data/clips/<source_id>/` передаётся **относительным путём от cwd генератора**, а `source_id` намеренно ASCII: OpenCV в генераторе на Windows ненадёжно открывает не-ASCII пути. Сейчас его кадрирование отключено, но без патча оно снова включится.
- Генератор нужен только для транскрипции и выбора моментов. Оркестратор передаёт env `LOCAL_SKIP_CROP=true`, его понимает только патч: генератор не режет видео, в `result.json` у моментов нет `clip_url`. Исходник берётся из `source_video_url`, путь относителен cwd генератора.
- Клип монтирует `render`: один ffmpeg на клип, `-ss/-to` до `-i`, `filter_complex` макета из `LAYOUTS`, `ass`, `loudnorm`, x264 veryfast, выход `short_NN.mp4` 1080x1920. Режимы для пользователя: auto, fit, crop. split и face бывают только внутри auto, их поля (рамка вебки, выражение слежения) подставляются в фильтр через `str.format`.
- `snap` подтягивает начало к ближайшему началу реплики `<исходник>.srt`, конец к ближайшему концу, только если граница не дальше `SNAP_MAX`, и добавляет `SNAP_PAD`. Без порога клипы раздувались: 25 с превращались в 47 с.
- Из того же `.srt` вырезаются субтитры во временный `.ass` (PlayRes 1080x1920), позиция по макету задаётся тегами `\pos` из `SUB_POS` и `TITLE_POS`. Стиль заголовка подставляется в `ASS_HEADER` из `TITLE_*` конфига. Ширину текста не меряем: `title_layout` сам режет длинный заголовок на две строки (`\N`, по словам ближе к середине) и уменьшает шрифт по длине длинной строки (`TITLE_LINE_CHARS_AT_100`, подобрано под Russo One с обводкой). Если строка всё же шире зоны, libass делит её ещё раз, и заголовок вырастает до 3–4 строк. Сменишь шрифт или обводку, подбери заново.
- ffmpeg запускается с cwd в папке клипа и получает `ass=<имя>:fontsdir=<относительный путь к fonts/>` без абсолютных путей, потому что двоеточие в `C:\` ломает синтаксис фильтров.
- В `fit` картинка ровно по центру по вертикали, заголовок привязан низом к её верхнему краю (`FIT_TOP`). Позиции рассчитаны на горизонтальный исходник 16:9.
- Все позиции текста считаются от безопасной зоны TikTok (`SAFE_*` в конфиге, константы `SAFE_CX`, `TEXT_TOP`, `TEXT_BOTTOM`, `FIT_TOP`). В split субтитры стоят под заголовком, а не у низа экрана: низ закрывает интерфейс TikTok, а чуть выше прицел (y=1344).
- `--layout auto`: `detect_faces` запускает `app/faces.py` python из venv генератора (OpenCV там уже есть, свой venv ради одного скрипта не заводили) и получает JSON с лицами раз в `AUTO_SAMPLE_SECONDS`. Решение принимает `pick_layout` на stdlib. Порядок: вебка → split с рамкой `cam_rect`. Вебка это маленькое лицо у края, которое стоит на месте не меньше чем в `AUTO_MIN_SHARE` замеров и при этом живее остальных таких лиц. Живость (`motion`) считает `faces.py`: средняя разница яркости в рамке лица с прошлым замером. Её ввели, потому что на ЭВЕЛОНЕ YuNet стабильно и с большей уверенностью находит аниме-аватар над вебкой. Аватар меняется реже живого лица, а совсем неподвижные картинки отсекает `AUTO_STILL`. Абсолютного порога между аватаром-слайдшоу и вебкой нет, поэтому лица сравниваются между собой внутри клипа. Дальше крупное лицо у центра → внутренняя раскладка `face`: x окна 9:16 задаёт то же слежение, что в crop (`track_faces`, отдельный проход 3 раза в секунду со склейками только для клипов face). Замеры раз в секунду для `pick_layout` не трогаем: на них откалиброваны пороги, в том числе `AUTO_STILL` по разнице кадров через секунду. Для IRL, где человек ходит и медиана ничего не говорит, есть второе правило: face, если в `AUTO_IRL_SHARE` замеров лицо заметное (`AUTO_SMALL_FACE`) и не у края. Иначе fit. В нарезках стримов fit часто правильный исход: источник меняется внутри клипа (лицо во весь кадр, потом маленькая вебка), а раскладка одна на клип.
- Кадры для детектора `faces.py` берёт одним проходом ffmpeg по отрезку клипа (`-ss` до `-i`, `fps=1/step`, уменьшение), а не перемоткой OpenCV на каждый замер. Перемотка OpenCV декодирует от ключевого кадра, у 1080p60 с ключевыми кадрами раз в 5.5 с это 0.2 с на замер. Новый способ дал 1:24 → 0:23 на 292 с клипов.
- `render` первым фильтром ставит `fps='min(source_fps,OUTPUT_FPS)'`. На 60 fps исходника вся цепочка, особенно наложение `ass` и фон fit, обрабатывала вдвое больше кадров. Выражение с `source_fps` требует свежего ffmpeg (проверено на 9.0). Если детектор упал, клипы идут в fit, а его stderr пишется в лог.
- Ручной fit детектор лиц не запускает. Все режимы срезают чёрные полосы: `detect_bars` по `bar_rows` (кадр PGM в pipe, строка полосы, если её максимум не ярче `BARS_BLACK`; полосы признаются при согласии кадров и симметрии). Рамка уходит первым фильтром в `render` и в `faces.py` (`crops`). `bar_rows` берёт ключевой кадр (`-skip_frame nokey`, один поток), после последнего ключевого кадра файла он пуст, тогда повтор с обычной перемоткой.
- crop и face в auto монтируются раскладкой `face`, выражение строит `crop_track` через `track_faces`. `faces.py` с опцией `scene` в том же проходе ffmpeg вторым выходом ищет склейки (`select` по scene, `metadata=print` в stderr). Дальше `scenes` (склейки и слияние коротких), `scene_targets` (главное лицо с гистерезисом, пара), `fill_gaps`, `follow` (мёртвая зона и два сглаживания с шагом `FOLLOW_STEP`), `knots_expr`. Выражение это дерево `if(lt(t,mid),...)` двоичным поиском (`bisect_expr`): eval ffmpeg падает на цепочке глубже ~90 узлов, и вложенные `if` подряд, и сумма `a+b+...` на 100+ слагаемых. В select склеек всегда проходит первый кадр (`+eq(n,0)`), иначе в клипе без склеек выход null падает. Граф `render` пишет в файл `.filter` и отдаёт через `-/filter_complex`, иначе длинное выражение упирается в лимит командной строки Windows.
- `cut.bat` намеренно ASCII и только вызывает `cut --ask`, вопросы задаёт Python. cmd неправильно разбирает UTF-8 bat с кириллицей после `chcp 65001`: строки съезжают, `set /p` молча получает пустые ответы.
- Патч генератора (`patches/`) даёт запросам к Gemini таймаут 2 минуты и 5 попыток (без него google-genai ждёт вечно и не повторяет 503), добавляет `LOCAL_SKIP_CROP`, требует в промпте писать `title` и `hook_sentence` на языке транскрипта, подставляет критерии из файла `HIGHLIGHTS_PROMPT_FILE` (оркестратор передаёт `prompts/highlights.txt`), режет длинное видео на куски по 10 минут вместо 20 и просит в куске по кандидату на минуту (за вызов модель всё равно отдаёт 5–10), и чинит видео длиннее 30 минут. Без последней правки куски уходили в Gemini с абсолютным временем, и с третьего куска генератор падал. Теперь сломанный кусок пропускается.
- `HIGHLIGHTS_TIMEOUT` плюс `HIGHLIGHTS_TIMEOUT_PER_HOUR` на час видео страхуют от зависания: оркестратор убивает генератор, если выбор моментов идёт дольше. Длину видео `run_generator` берёт из строки генератора `... Ns of audio`. Замер: синтетический транскрипт на 3 часа разбирается за 115 с (14 вызовов Gemini по ~9 с) при кусках по 20 минут, с кусками по 10 вызовов вдвое больше. Конец этапа определяется по строкам вывода генератора (`GENERATOR_STAGES`). Если генератор поменяет эти строки, замер этапов и таймаут перестанут срабатывать.
- `GEMINI_MODEL=gemini-3.5-flash-lite` в `.env` генератора: полные flash-модели часто отвечают 503 high demand. `LOCAL_WHISPER_MODEL=base`: субтитры выключены, а для выбора моментов точности base хватает, при этом он в ~8 раз быстрее small.
- `prompts/highlights.txt` это текст для модели, а не код: правится напрямую. После правки прогони выбор моментов на 2–3 видео с кэшем и сравни распределение score.
- Заголовки генератора черновые. После `pick_moments` и `snap` функция `rewrite_titles` одним запросом через `ask_gemini` (`app/gemini.py`, python и cwd генератора, ключ и `GEMINI_MODEL` из его `.env`) переписывает все заголовки по транскрипту клипа из `.srt`. Правила в `prompts/titles_stream.txt` и `prompts/titles_film.txt`, файл выбирает `--type`. Ник (`--streamer`) и формат JSON-ответа добавляет код, в файлы правил их не пишем. Поле `kind` (мнение, ситуация, сцена) только пишется в лог. Фильтр Gemini (PROHIBITED_CONTENT, не настраивается) блокирует и сочетание клипов, каждый из которых проходит по отдельности: на IRL ЭВЕЛОНА 10 клипов стабильно не проходили вместе. `gemini.py` выходит с кодом 3 (`GEMINI_BLOCKED`), и `rewrite_titles` делит запрос пополам. Одиночный заблокированный клип выкидывается. Любая другая ошибка или клип без заголовка роняет `make_clips` целиком: черновики генератора не проходят правил и попали бы в TikTok. flash-lite местами додумывает факты («месть бывшей») вопреки правилу.
- Клипы выбирает `pick_moments` из всех кандидатов `result.json` (`highlights`, а не `shorts`): score от `CLIP_MIN_SCORE`, не меньше минимума из таблицы `CLIPS_MIN` по длине исходника (`transcript.duration` в `result.json`) и не больше `CLIPS_MAX`. Генератору передаётся `--num-clips CLIPS_MAX` только для того, чтобы промпт просил больше кандидатов (по патчу кандидат на минуту, до 15 за вызов). Оценки у модели сжаты в 78–96, поэтому порог чувствительный: на единицу меняет число клипов заметно.
- В venv генератора закреплены `av==18.1.0` и `opencv-python<5` (причины в README). Этот же OpenCV нужен `app/faces.py`.

**Аплоадер** (`tools/tiktok-uploader`, `cli.py upload`):
- Это autotok 2.x. Node.js не нужен, сессии лежат в `~/.autotok/accounts`.
- `-sc` — секунды от текущего момента. Расписание держит сам TikTok, постоянно работающего планировщика нет.
- Коды выхода: 0 — успех, 2 — ошибка валидации, 1 — прочие ошибки.
- Ошибку `PublishUncertainError` (пост мог уйти) распознаём только по подстроке `check the account` в выводе (`UNCERTAIN_MARKER`). Если autotok поменяет текст этой ошибки, детекция сломается.

**Очередь** — одна таблица `clips`, статусы `pending`/`uploaded`/`failed`/`unknown`:
- Слот назначается в момент `upload`, а не при `process`.
- Занятыми считаются слоты клипов в статусах `uploaded` и `unknown`; `failed` слот освобождает.
- Перед вызовом аплоадера строка заранее ставится в `unknown`. Так прерванная заливка не повторится сама. Traceback в выводе тоже даёт `unknown`.
- **`unknown` никогда не ретраится автоматически**, только вручную через `retry`. Это инвариант против дублей постов.
- Повторный `process` того же исходника (абсолютный путь или URL) — no-op.

**Время**:
- `TZ` — фиксированный сдвиг UTC+10 (Владивосток), а не `ZoneInfo`: на Windows `ZoneInfo` требует пакет tzdata.
- `MIN_LEAD` = 20 минут: минимум TikTok 15 минут плюс запас на заливку. Без запаса autotok сам сдвинет публикацию с границы слота.
- `MAX_LEAD` = 10 дней: части аккаунтов TikTok не даёт планировать дальше.
- Запланированное видео не может быть приватным, поэтому любой тест `upload` — это настоящий публичный пост.
